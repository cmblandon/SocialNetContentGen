# Step 4.3 Report - Manual Endpoint Testing with curl

- Date: 2026-09-06
- Change: research-query-scoping
- Agent: Claude Code

## Test Environment
- Backend: an already-running `uvicorn` process on port 8000 (started outside
  this session, confirmed healthy via `GET /health` → `{"status":"ok"}`).
  Reused as-is, not restarted.
- **Real `ANTHROPIC_API_KEY`, `JINA_API_KEY`, and `FIRECRAWL_API_KEY` are now
  configured** in `.env` (unlike earlier in this session) — this is a live
  environment, not an isolated test one, and it holds real operator data
  (`data/knowledge_base/editorial_memory/fuentes.md` has two real
  operator-configured source URLs). Calling `POST /research/run` with those
  real URLs would trigger real Jina/Anthropic API calls (cost, latency) and
  mutate the user's real `casos_cubiertos.md`/DB — unnecessary for what this
  task actually needs to verify, which is request/response wiring for the new
  `query` field, not third-party scraper/LLM integration (a pre-existing,
  unrelated concern this change doesn't touch).
- **Approach taken**: called the real, running endpoint with a `source_url`
  that fails the official-source allowlist check (`https://example.com/not-an-official-source`)
  — `ResearchAgentUseCase.discover()` discards this before ever invoking a
  scraper (see `specs/research-agent/spec.md`), so both calls below exercise
  the actual live FastAPI request-validation and response-construction path
  with zero external API calls and zero data mutation, regardless of `query`.
  This directly satisfies task 4.3's "fake scrapers ... if real API keys
  aren't configured" escape hatch in spirit — here the equivalent zero-cost
  substitute was an allowlist-rejected URL rather than a throwaway script,
  since real keys being present didn't change what needed verifying (the
  request schema, not the scrapers).

## Commands and Results

1. **Without `query`** (today's existing shape, unchanged):
   ```
   curl -X POST http://localhost:8000/research/run \
     -H "Content-Type: application/json" \
     -d '{"source_urls": ["https://example.com/not-an-official-source"]}'
   ```
   → `200 {"documents_reviewed":0,"stories_created":0,"chapters_generated":0,"pending_approval_platform_version_ids":[],"discarded_document_ids":[]}`

2. **With `query`** (the new field):
   ```
   curl -X POST http://localhost:8000/research/run \
     -H "Content-Type: application/json" \
     -d '{"source_urls": ["https://example.com/not-an-official-source"], "query": "missile silo incidents"}'
   ```
   → `200 {"documents_reviewed":0,"stories_created":0,"chapters_generated":0,"pending_approval_platform_version_ids":[],"discarded_document_ids":[]}`

**Result: identical response shape and status in both cases** — confirms
`ResearchRunRequest` accepts the optional `query` field without any schema
error, and its presence/absence has no effect on the response contract, per
design.md's backward-compatibility goal.
