## Test Results
- `e2e/covered-cases.spec.ts` — **1 passed** on the first run (no changes
  needed beyond the `/approvals` → `/` URL fix from task 8.2).
- `e2e/approval-to-calendar.spec.ts` — required one fix and one reseed
  during verification, both documented here since they reveal real
  findings, not just "it passed":
  1. **Test bug found and fixed**: the spec clicked "Publicar en TikTok"
     then immediately called `page.goto("/calendar")`. Since `page.goto`
     is a full browser navigation, it aborted the in-flight publish
     `fetch` before the backend received it, so the calendar showed
     nothing published. Fixed by asserting the "Publicar en TikTok" button
     disappears (replaced by a status chip either way) before navigating —
     this only proceeds once the request has actually resolved. This is a
     genuine test-authoring bug, not a product bug: the UI never claimed
     the publish completed before the button changed state.
  2. After that fix, a second run had to reseed a fresh pending chapter,
     because the first (failing) run's "Aprobar" click had already
     approved all four platform versions of the seeded chapter against
     the real database before the test failed — a real side effect from a
     real backend, correctly persisted. Confirms the explicit
     approve/publish decoupling (design.md Decision 1) works end-to-end
     against a live server, not just the FastAPI test client.
  3. Final run (fresh seed): **1 passed**. The publish attempt itself
     failed at the network layer (`status failed` in `calendario.md`,
     `error_message` from a connection refusal), since no real Postiz
     instance runs in this environment — expected and immaterial to the
     test, which only asserts a `PublishRecord` exists for `tiktok`
     (created regardless of success/failure, per `specs/publishing`'s
     single-attempt-independent-of-outcome recording behavior).

Both specs green on the final run:
