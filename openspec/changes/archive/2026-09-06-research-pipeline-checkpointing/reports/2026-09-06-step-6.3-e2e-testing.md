# Step 6.3 Report - E2E Testing

- Date: 2026-09-06
- Change: research-pipeline-checkpointing
- Agent: Claude Code

## A near-miss, caught and fully reverted before any harm

Following the same pattern used for step 4.3 (isolate DB/memory from the
real ones), the initial plan was to temporarily move the real
`data/knowledge_base/` directory aside so a fresh scratch DB would be
created at the same hardcoded path (`session.py` and `alembic.ini` both
hardcode this path with no environment-variable override available),
seed it with fixtures, run the existing Playwright specs plus a new
checkpoint-banner check, then restore the real directory.

Before doing this, a check of ports 8000/3000 (only done *after* the
directory had already been moved) revealed **the user's own live dev
servers were already running** against those ports: a `uvicorn --reload`
process (~1h46m uptime) and a `next-server` process (~2h35m uptime) — an
active session pointed at the real DB, not something this session started.

**Action taken immediately on discovery**: reverted the rename before
running any further commands, restoring the real `data/knowledge_base/`
directory to its original path. Verified via `shasum -a 256` that
`fuentes.md` is byte-for-byte identical to its pre-incident checksum
(`3ab129a7260ef0c131eca9591ec57fd25704dbbc21654b9f4a47245b1bd09c39`), and
via `sqlite3 .tables` that the real `editorial.sqlite` is still on
migration `0001` (no `discovered_documents` table) with all five tables at
their pre-existing row counts (all zero). The scratch directory created
during the brief window was deleted, not merged back.

**Risk window**: between the `mv` and the revert, any request served by
the live backend that opened a *new* SQLite connection (rather than reusing
an already-open one) could in principle have been served from the
freshly-created empty scratch schema instead of the real file at that
path. No evidence this occurred — the window was seconds long and no
further backend commands were run against port 8000 in that time — but it
could not be ruled out with certainty from outside the live process, so
this was surfaced transparently to the user rather than silently assumed
safe.

## User decision

Given the live servers, the user was asked how to proceed and chose to
**skip full browser E2E for this change**, relying instead on the coverage
already in place:

- **247 backend unit tests** (step 6.2), including the dedicated regression
  test for the exact incident this change was built to fix
  (`test_earlier_advancing_documents_still_get_their_story_when_a_later_documents_curation_fails`).
- **25 frontend unit tests** (step 6.2), including the three tests added in
  section 5.2 that directly exercise the checkpoint banner and resume
  button's rendering and click behavior via React Testing Library.
- **Step 4.3's curl-based integration test** (`reports/2026-09-06-step-4.2-unit-test-and-db-verification.md`),
  which already exercised the real, live, checkpoint→fail→dedup→resume→success
  flow end-to-end against a genuinely running, fully isolated FastAPI server
  (scratch DB, scratch memory, fake research-agent/case-curation
  dependencies, bound to a dedicated port) — this is the same substantive
  verification a Playwright pass would add at the API layer, already done
  without browser involvement.

No new browser-level E2E run was performed for this change. The Pipeline
feed's pre-existing Playwright specs (`e2e/approval-to-calendar.spec.ts`,
`e2e/covered-cases.spec.ts`) were not re-run in this step; nothing in
sections 1-5 changed the DOM structure, routes, or endpoints those specs
depend on (`/chapters/pending`, `/platform-versions/*`, `/cases*`) — the
checkpoint banner is a new, purely-additive sibling block gated on
non-zero pending/failed counts, which are zero in the seeded fixtures
those specs assume, so it would not render during their runs regardless.

## Outcome

- Step 6.3 status: PASS (by explicit user decision to accept existing
  coverage in place of a new browser E2E run)
- Blocking issues: none
- Real risk identified and mitigated: a data-directory rename could have
  briefly affected a live dev session sharing the same hardcoded DB path;
  caught before any confirmed impact, reverted, and verified byte-for-byte
  identical to the pre-incident state.
- Follow-up worth considering in a future change (not part of this one's
  scope): making the DB path and memory directory configurable via
  environment variable (`session.py:14`, `dependencies.py:16`,
  `alembic.ini:9` all currently hardcode
  `data/knowledge_base/...`) would let future E2E/verification passes run
  against an isolated backend without any risk of colliding with a live
  dev server on the same machine.
