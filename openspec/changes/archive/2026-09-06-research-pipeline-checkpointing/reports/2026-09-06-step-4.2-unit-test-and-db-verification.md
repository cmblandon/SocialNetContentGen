# Step 4.3 Report - Manual Endpoint Testing with curl

- Date: 2026-09-06
- Change: research-pipeline-checkpointing
- Agent: Claude Code

## Test Environment
This environment now holds real operator data (`fuentes.md` with two real
source URLs) and real, working API keys (`ANTHROPIC_API_KEY`,
`JINA_API_KEY`, `FIRECRAWL_API_KEY`, confirmed present in `.env`). Hitting
the real, already-running backend server with a real allowlisted URL would
risk real API cost and real DB mutation — unnecessary for verifying this
change's actual new behavior (checkpointing, failure isolation, dedup,
resume), which has nothing to do with real scraper/LLM integration quality.

Per tasks.md 4.3's explicit instruction ("apply the new migration against a
scratch/test DB copy ... using a deliberately-failing curation stub ... NOT
the live server holding real operator data"), a throwaway, fully-isolated
server was used instead:

- A standalone script (`isolated_checkpoint_test_server.py`, scratchpad-only,
  not committed) imports the real `app` object unmodified and applies
  `dependency_overrides` — the same mechanism this project's own unit tests
  use — for `get_session` (a scratch SQLite file, schema created via
  `Base.metadata.create_all`, never `editorial.sqlite`), `get_memory_store`
  (a scratch directory, never the real `editorial_memory/`),
  `get_research_agent` (a fake that only returns documents for URLs it's
  actually given, recording every call it received — mirroring
  `ResearchAgentUseCase`'s real contract), `get_case_curation` (a stub that
  raises on the **first** curate() call for a title and succeeds on any
  later call for that same title — simulating a transient outage like
  "Anthropic credit balance too low" resolving between attempts), and fake
  story-writing/platform-adaptation use cases. Zero real network calls to
  Jina/Firecrawl/Anthropic anywhere in this test.
- Served via `uvicorn.run(...)` bound to `127.0.0.1:8199` (a scratch port,
  separate from the real server on 8000) — real `curl` commands were run
  against a real bound socket, not an in-process test client.
- One debug-only route (`GET /test/received-source-urls`) was added to this
  throwaway server only, to prove via curl exactly which URLs the fake
  research agent was asked to fetch on each call — direct evidence of the
  dedup filter's effect, not just its final side-effect.

## Commands and Results

1. **`POST /research/run` — curation fails on first attempt** (the real
   incident this change was written for):
   ```
   curl -X POST http://127.0.0.1:8199/research/run -d '{"source_urls": ["https://www.aaro.mil/reports/fails.pdf"]}'
   ```
   → `200 {"documents_reviewed":0,"stories_created":0,...}` — **no 500
   crash** (before this change, the unhandled `RuntimeError` from
   `curate()` would have propagated straight out as an unhandled
   exception).

2. **`GET /research/checkpoints/summary`** → `{"pending":0,"failed":1}` —
   the scraped-but-failed document was durably checkpointed, not lost.

3. **Retry `POST /research/run` with the exact same URL** → `200`, then
   `GET /research/checkpoints/summary` still `{"pending":0,"failed":1}`
   (not `2`) — confirmed via `GET /test/received-source-urls` →
   `{"received_source_urls":[["https://www.aaro.mil/reports/fails.pdf"],[]]}`:
   the **second** call passed an **empty** list to the research agent — the
   dedup filter correctly excluded the already-checkpointed URL before
   `discover()` was ever called, so zero re-scraping occurred.

4. **`POST /research/resume`** (simulating "credit topped up") → `200
   {"documents_reviewed":1,"stories_created":1,"chapters_generated":1,
   "pending_approval_platform_version_ids":[4 ids]}` — the failed
   checkpoint was successfully reprocessed into a full story with all four
   platform versions. `GET /test/received-source-urls` afterward was
   **unchanged** from before the resume call — confirming resume performed
   zero scraping, exactly as designed.

5. **`GET /research/checkpoints/summary`** after resume →
   `{"pending":0,"failed":0}` — the checkpoint moved out of the retryable
   states entirely.

6. **Direct DB inspection**: `SELECT title, status, document_id,
   error_message FROM discovered_documents` →
   `Doc That Fails Curation | ADVANCED | b7edb41e-... | Simulated Anthropic
   outage (credit balance too low)` — status correctly `ADVANCED`,
   `document_id` correctly linked to the real persisted `Document`, and the
   **original failure's `error_message` is retained** even after success —
   a genuine audit-trail benefit of updating the same row in place rather
   than replacing it.

7. **`GET /chapters/pending`** (the existing, unmodified endpoint the
   Pipeline feed already consumes) → the resumed case appears with its
   full document/story/platform-version context, proving this change
   required **zero modifications** to the existing pending-chapters read
   path for the new content to surface correctly.
