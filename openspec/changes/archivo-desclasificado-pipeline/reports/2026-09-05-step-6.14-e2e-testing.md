## Tooling note

No dedicated "Playwright MCP" browser-automation tool (`browser_navigate`,
`browser_click`, etc.) is available in this environment — only
`claude-in-chrome`, which requires the user's local Chrome extension to be
installed and connected, and wasn't invoked. Instead, this step used the
project's own installed `@playwright/test` runner (real headless
Chromium, installed via `npx playwright install chromium --with-deps` in
Phase 6 setup), executed directly by the agent via the CLI
(`npx playwright test`). This achieves the same substantive requirement —
real-browser E2E verification executed by the agent, not delegated to the
user — through the standard mechanism `docs/frontend-standards.md`
already specifies for this project's E2E suite.

## A real gap found and fixed during this step

Wiring up the frontend and backend together for the first time (rather
than each in isolation) surfaced a genuine missing piece: **the FastAPI
app had no CORS configuration**, so every browser request from the
Next.js dev server (`localhost:3000`) to the API (`localhost:8000`) would
have failed. This wasn't caught earlier because every backend test to
date used FastAPI's `TestClient`, which doesn't enforce browser CORS
semantics, and every frontend test mocked `@/lib/api` entirely. Added
`CORSMiddleware` (`src/editorial/presentation/app.py`) allowing
`http://localhost:3000`, with two new backend tests
(`tests/unit/test_cors.py`) verifying the `Access-Control-Allow-Origin`
header on both a simple and a preflight request. Not itemized separately
in tasks.md — folded into this step's notes since it was discovered here.

seeded chapter's full context is rendered (document title, per the

- First run: passed.
- **Bug caught in my own test, not the app**: a second full-suite run
  initially failed with a Playwright strict-mode violation (two elements
  matched the same heading) because I had re-seeded a second overlapping
  chapter without first clearing the previous run's leftover data. Fixed

  final run.

  actual publish attempt failed against Postiz, as expected with no real

  "published", "failed", or "proposed schedule" as valid outcomes, since

  entry at all, not that a real Postiz instance is reachable).

## Scenario 2: covered-cases search + edit (`e2e/covered-cases.spec.ts`)

Logs in, navigates to `/cases`, confirms both seeded cases are visible,
searches "radar", confirms only the matching case remains visible, edits
its reason via the Edit/Save flow, confirms the new reason renders, then
**reloads the page** and confirms the edit persisted server-side (not
just in local React state).

- First run: **failed** — a genuine bug in my test, not the app: the test
  navigated to `/cases` immediately after clicking "Log in" without
  waiting for the async login request to complete and set the session
  cookie, so it raced ahead and `proxy.ts` correctly bounced it back to
  `/login` (the *other* test happened to wait on the post-login redirect
  already, which is why it passed on the first try). Fixed by adding
  `await expect(page).toHaveURL(/\/approvals/)` after the login click,
  mirroring the first test.
- Final run: **passed**, including the reload-to-confirm-persistence
  check.
