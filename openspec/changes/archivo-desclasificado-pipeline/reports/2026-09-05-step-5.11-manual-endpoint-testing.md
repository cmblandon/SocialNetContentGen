- Result: PASS

### GET /publish-records — before any publish attempt

- Result: PASS

### Approve PV2 — optimal time now configured
- Setup: appended `optimal_time:tiktok=18:00` to the real `calendario.md`.
- Command: `curl -s -i -X POST http://127.0.0.1:8126/platform-versions/<PV2>/approve`
- Response: `200`, `{"status":"approved","publish_outcome":{"published":false,"error_message":"Illegal header value b'Bearer '","proposed_time":null}}`
- **Observation**: with no `postiz_api_key` configured, the adapter sends `Authorization: Bearer ` (empty token), which `httpx` rejects client-side as an illegal header value before any network call is made. `PostizPublisherAdapter`'s broad `except Exception` still converted this into a clean `PublishResult(success=False, ...)` rather than crashing the request — the defensive design worked correctly even for a failure mode (a local header-validation error) I hadn't specifically anticipated, not just for actual network failures.
- Result: PASS (verified the adapter never raises, and the failure is surfaced correctly, per specs/publishing/spec.md's "report failures" requirement)

### GET /publish-records — after the failed attempt
- Command: `curl -s -i -X GET http://127.0.0.1:8126/publish-records`
- Response: `200`, one record: `{"platform_version_id":"<PV2>","platform":"tiktok","status":"failed","external_post_id":null,"scheduled_at":"2026-09-05T18:00:00","published_at":null,"error_message":"Illegal header value b'Bearer '"}`
- Result: PASS

### Approve PV2 again — no silent retry
- Command: `curl -s -i -X POST http://127.0.0.1:8126/platform-versions/<PV2>/approve`
- Response: `409 Conflict`, `{"detail":"PlatformVersion <PV2> was already decided (status='failed')."}`
- Result: PASS — confirms no automatic or manual re-publish happens without a fresh, explicit approval path; the failed `PlatformVersion` is left in `FAILED`, which `run_if_approved`/`_require_pending_review` both refuse to act on again.
